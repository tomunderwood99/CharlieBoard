# Quick Start Guide

Get your MBTA LED display running in under 10 minutes with the automated setup script.

## Prerequisites

1. Raspberry Pi with Raspberry Pi OS installed and booted
2. WiFi/network configured
3. SSH access to your Pi
4. Hardware connected (WS2812B LEDs, 5V power supply, common ground)

---

## Installation

### Step 1: Clone Repository

```bash
sudo apt update && sudo apt install -y git python3-pip
cd ~
git clone https://github.com/tomunderwood99/CharlieBoard.git
cd mbta_led_controller

# Optional: Remove hardware folder to save space
rm -rf hardware/
echo "hardware/" >> .git/info/exclude
```

### Step 2: Run Setup Script

```bash
chmod +x deployment/quick_start/setup_mbta_controller.sh
sudo ./deployment/quick_start/setup_mbta_controller.sh
```

### Step 3: Answer Prompts

| Prompt | Required | Default | Notes |
|--------|----------|---------|-------|
| Install WiFi Helper | No | No | Captive-portal WiFi setup on first boot ([details](#headless-wifi-setup-optional)) |
| MBTA API Key | Yes\* | — | Free at [api-v3.mbta.com](https://api-v3.mbta.com/) |
| Line | No | Red | Red, Blue, Orange, or Green |
| Timezone | No | Eastern | Select from menu |
| Bedtime Start/End | No | 22:00/06:00 | Auto-off hours |
| Brightness | No | 0.5 | 0.0–1.0 |
| LED Test | No | Yes | Tests hardware |
| Start Services | No | Yes | Start immediately |

\* The MBTA API key prompt becomes optional when the WiFi helper is installed — you can leave it blank and enter the key through the captive portal on first connection.

### Step 4: Done!

Access web interface at `http://your-hostname.local:8000`

### Optional Enhancements

**Raspberry Pi Connect** – Secure remote access from anywhere via web browser:
```bash
sudo apt install rpi-connect
rpi-connect signin
```
Then access your Pi at [connect.raspberrypi.com](https://connect.raspberrypi.com). See [official docs](https://www.raspberrypi.com/documentation/services/connect.html).

**nginx Reverse Proxy** – Access at `http://hostname.local` without the port number. See [nginx setup guide](../../docs/nginx_reverse_proxy_setup.md).

## Headless WiFi setup (optional)

Designed for boards that move between locations. The setup script can install [`tomunderwood99/headless_wifi_helper`](https://github.com/tomunderwood99/headless_wifi_helper) alongside CharlieBoard so the Pi can reconfigure WiFi (and the MBTA API key) from a phone — no re-flashing or wired connection required.

> **Requires Raspberry Pi OS Trixie.** The helper hard-depends on NetworkManager as the network backend (the default on Trixie). Older Bookworm/Bullseye images using `dhcpcd` + `wpa_supplicant` are *not* supported, and the helper's installer will fail. Once installed, CharlieBoard's runtime WiFi recovery (`monitoring/network_monitor.py`) and reboot-loop recovery (`monitoring/health_monitor.py`) also assume NetworkManager. Pass `--no-wifi-helper` to skip if you're not on Trixie.

### How it works

At boot, the helper's `wifi_configurator.service` runs **before** `network-online.target` — and CharlieBoard's services run **after** it — so the MBTA display always waits for WiFi to be ready.

```
Boot
 └─ NetworkManager.service
     └─ wifi_configurator.service           ← waits up to ~30s for wlan0
         ├─ wlan0 associated → exit 0
         └─ no association  → AP at 192.168.4.1, blocks until user reboots
     └─ network-online.target
         ├─ mbta_display.service
         └─ mbta_monitor.service
```

When the AP is up, connect to it from a phone (most devices auto-launch the captive portal; otherwise open `http://192.168.4.1`), pick a network, enter credentials, optionally paste an MBTA API key, hit **Save Credentials**, then **Reboot Now**. The helper writes the API key into CharlieBoard's `.env` as `MBTA_API_KEY=…` before the reboot.

### Enabling it

The setup script asks interactively (default **No** — just press Enter to skip). To skip the prompt entirely in either direction:

```bash
sudo ./deployment/quick_start/setup_mbta_controller.sh --with-wifi-helper
sudo ./deployment/quick_start/setup_mbta_controller.sh --no-wifi-helper
```

Additional flags forwarded to the helper's own `setup.sh`:

| Flag | Default | Purpose |
|------|---------|---------|
| `--wifi-helper-dir <path>` | `/home/<user>/headless_wifi_helper` | Where to clone the helper repo. |
| `--ap-ssid <ssid>` | `PiWifiSetup` | Captive-portal AP SSID. |
| `--ap-password <pw>` | autogenerated 16-char random | AP password (12+ chars required by the helper's policy). |

When `--with-wifi-helper` is selected, the MBTA API key prompt becomes optional — leave it blank during setup and enter it through the captive portal on first connection.

### Runtime behavior

If WiFi is lost while CharlieBoard is running, `monitoring/network_monitor.py` first tries to bounce `wlan0` in-process via `nmcli device disconnect/connect` (or `ip link` on non-NetworkManager systems). If that fails, `monitoring/health_monitor.py` will eventually reboot the Pi (the same path it already uses for unhealthy systems), and on the next boot the helper detects the missing WiFi and brings up the captive portal automatically.

The health monitor additionally guards against an "associated-but-blackholed" reboot loop: if `wlan0` is associated to a known SSID but no public Internet probe is reachable (bad upstream link, captive portal we can't authenticate against, ISP outage on that SSID), the monitor deletes the active NM connection just before rebooting. On the next boot the helper sees no STA association and opens the captive portal at `http://192.168.4.1` so you can pick a different network — instead of the Pi silently re-associating to the same dead SSID and rebooting again. The probe deliberately avoids the MBTA API, so an MBTA-side outage will *not* cause us to wipe your WiFi config. This safety net only activates when `wifi_configurator.service` is installed; without the helper, the connection profile is preserved across reboots.

### Diagnostics

```bash
systemctl status wifi_configurator.service
sudo journalctl -u wifi_configurator.service -f
```

See the helper's [README](https://github.com/tomunderwood99/headless_wifi_helper/blob/main/README.md) for additional helper configuration (regulatory domain, hand-edited unit overrides, etc.).

## What the Script Does

1. Updates system and installs packages
2. Creates Python virtual environment
3. Installs dependencies
4. Creates `.env` configuration
5. Configures and installs systemd services
6. Sets up convenience commands (`display_status`, `display_reboot`)
7. Optionally installs the headless WiFi helper (`wifi_configurator.service`)
8. Optionally tests LED hardware

---

## After Setup

### Quick Commands

```bash
source ~/.bashrc        # Load aliases (first time)
display_status          # Check system status
display_reboot          # Restart services
```

### Service Management

```bash
sudo systemctl status mbta_display.service
sudo systemctl restart mbta_display.service
sudo journalctl -u mbta_display -f    # Live logs
```

### Change Configuration

Use the web interface (easiest) or edit directly:
```bash
nano ~/mbta_led_controller/.env
sudo systemctl restart mbta_display.service
```

## Troubleshooting

For detailed troubleshooting, see [Operations & Troubleshooting](../../docs/operations_and_troubleshooting.md).

### Quick Checks

| Issue | Command |
|-------|---------|
| LED test | `sudo -E venv/bin/python tests/red_test.py` |
| Service status | `sudo systemctl status mbta_display.service` |
| View logs | `sudo journalctl -u mbta_display -n 100` |
| Find IP | `hostname -I` |
| Test API | `curl "https://api-v3.mbta.com/vehicles?api_key=YOUR_KEY"` |

### Common Issues
- **LEDs don't light**: Check wiring (GPIO 18, common ground)
- **Service won't start**: Check `.env` exists and API key is valid
- **Can't access web**: Try IP address instead of hostname

## What Gets Installed

### System Packages
- python3, python3-pip, python3-venv, python3-dev, git

### Python Packages (in venv)
- Flask, requests, sseclient, rpi-ws281x, adafruit-blinka, adafruit-circuitpython-neopixel, pytz

- `mbta_display.service` - Main display and web interface
- `mbta_monitor.service` - Health monitoring (auto-restarts main service)
- `daily_reboot.timer` - Daily 3 AM reboot for stability
- `wifi_configurator.service` *(optional, only with `--with-wifi-helper`)* - Captive-portal WiFi setup at boot

- `~/mbta_led_controller/.env` - Configuration
- `~/mbta_led_controller/venv/` - Python environment
- `~/mbta_led_controller/logs/` - Application logs
- `~/headless_wifi_helper/` *(optional)* - Cloned helper repo, used by `wifi_configurator.service`

## For Developers: Script Architecture

### Design Philosophy

Only 3 critical inputs required:
1. **MBTA API Key** - Cannot function without
2. **Line** - Which line to display (default: Red)
3. **Timezone** - For scheduling (default: Eastern)

All other settings have defaults and can be changed via web interface.

### Path Detection

```bash
ACTUAL_USER=${SUDO_USER:-$USER}
PROJECT_DIR=$(pwd)
VENV_PATH="$PROJECT_DIR/venv"
```

Service files updated dynamically via `sed`:
```bash
sed -i "s|WorkingDirectory=.*|WorkingDirectory=$PROJECT_DIR|g" deployment/systemd/*.service
```

### Why sudo Required
- Installs system packages
- Modifies timezone
- Copies files to `/etc/systemd/system/`
- Services need GPIO access

### Customization Points
- **Venv name**: Modify `VENV_NAME` variable
- **Defaults**: Change `${VAR:-default}` patterns
- **Validation**: Enhance with regex/pattern matching
